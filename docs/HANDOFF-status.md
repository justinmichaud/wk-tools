# HANDOFF — status while a command runs

Owed: every long-running command reports its progress the same way, and
`wk status` reads it.

- [ ] one progress record per running command (`wk pi bench`, `wk ab`, `wk sysimage build`, `wk sysimage webkit`, `wk build`, `wk bench`): what step it is on, of how many, since when, and the log to follow -- written where `wk status` reads a build's `alive: [n/m] (last output Xs ago)` today, and dying with the command (a lock is not state) [decision: one shape for every command, in lib/]
- [ ] `wk pi bench` prints a line per iteration and a heartbeat while a run is silent (run-benchmark logs "Start the iteration i of n"; today the round line is the last word for up to the plan's timeout), and `wk ab` prints which board/round it is on -- from the same record, not a second print [needs the record above]
- [ ] `wk status` shows every running command's record in the fleet/bench block (today it names only the latest bench result directory, and a detached buildroot or yocto image stage shows as `build=none`, so `wk status <ws> --wait` returns at once) [needs the record above]
- [ ] container/broker/wk-broker.py writes its own key=value record per request (`$(wk_state_dir)/broker/<rid>/status`, read back by `in_flight` and `request_status`), which is a second record shape for a long-running job. lib/task.sh's shape lives under `$WK_STORE/task`, and on a macOS workstation that is the podman VM's store, which the host the broker runs on cannot write. lib/task.sh answers that with `wk_record_dir` (lib/store.sh), which diverts the one store no host command can write -- the podman machine's, what a macOS workstation's default resolves to -- and leaves every store a command was pointed at alone. Both shapes now live under `$(wk_state_dir)` there; what is left is that they are still two shapes for one job [no hardware needed]
- [ ] `t_ws_dir <name>` -- the workspace's directory on the machine that holds it -- joins `t_src` and `t_tools` in the target interface (`lib/target.sh`), defaulting to `wk_ws_dir`; `targets/remote.sh:248`'s private `_remote_ws` becomes it at all seven of its call sites, and `targets/vm.sh` gives the tart guest's own path instead of inheriting the host's [no hardware needed]
- [ ] `cmd/build` writes the build log and the task record where the build runs, so the record's home does not depend on which machine `wk build` was typed on: `t_ws_dir` at `cmd/build:102` and `task_begin build target` at `cmd/build:330`. `t_task_put` then has nothing to copy and goes with its callers -- `lib/target.sh:173`, `targets/remote.sh:488`, `cmd/build:110,115,125,335`, `lib/watchdog.sh:196`; `tests/test_build_kill.py:530-562` and `tests/test_status.py:371` assert the copy today and assert the one home instead [needs `t_ws_dir`; touches the same liveness code as the `where=target` work in lib/task.sh]
- [ ] `cmd/status:155` and `cmd/logs:26` read that one record and that one log through the driver, one `t_exec` per record rather than one per field (`report_ws`'s batched git probe, `cmd/status:174`, is the shape), and a workspace whose machine does not answer reports unreachable rather than an empty BUILD column. Today a build started inside a tart guest leaves that column blank on the host, and `wk logs <ws>` on the host refuses with `no build log` [needs the two above]
- [ ] `capped` (`lib/common.sh:516`) closes fd 3 in its watchdog and takes the watchdog's children with it: `kill -TERM "$wd"` ends the subshell but not the `sleep` it forked, and that orphan holds the inherited write end of `wk status`'s records FIFO, so `status-view.py` blocks on EOF until the cap expires. Measured 2026-09-21: `wk status t` is 4.4s of record-gathering and 5.2s of dead wait, with `lsof` on the orphaned `sleep` showing `3w FIFO .../wk-status.*/records` [no hardware needed]
