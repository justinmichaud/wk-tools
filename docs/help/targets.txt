what a target is, and choosing container vs guest

TARGETS

  Every wk command acts on exactly one target: the environment where the work
  actually happens. Work never runs directly on a workstation -- that is the
  whole design, not a preference -- so "which target" is the first decision
  about any piece of work, and the only one you have to make twice.

  There are four kinds, behind one driver contract (lib/target.sh):

  container   rootless podman, an overlay checkout on a shared read-only base
              snapshot, no network interface, no host filesystem. The default,
              and the only sandboxed target on Linux. On macOS these live
              inside the podman VM.
  vm          a macOS guest under Tart, cloned from a golden base image. For
              the Apple ports, because macOS has no container primitive for
              macOS userspace. macOS hosts only.
  remote      a shared build machine, or another workstation. A plain checkout
              in your own home directory there; no sandbox of any kind.
  local       not a target you ask for: it is the degenerate driver a workspace
              uses on *itself*, which is what makes `wk build <config>` work
              from inside one.

  `container`, `vm` and `local` name both a driver and the one thing it drives.
  `remote` does not -- you can have several build machines -- so those targets
  are named after the machine instead:

      wk new bug-238                        # container, the default
      wk vm new apple-bug                   # == wk new apple-bug --target vm
      wk new big-build --target buildbox4   # a machine, by its own name

  See `wk help machines` for making a machine into a target in the first place.

  A workspace remembers what it was created with, so `--target` belongs to
  `wk new` and to nothing else:

      wk build bug-238 jsc-release      # resolved from the registry
      wk ls / wk status                 # every target at once, in one listing
      wk <command> --explain            # what this command would act on

  Only the target changes; the vocabulary does not. `wk build`, `run`, `test`,
  `logs`, `enter`, `rm` mean the same thing on all of them, and the job count
  and nice level are always derived from the machine that will do the work --
  the guest's own memory for a vm, the shared box's live load average for a
  remote, the cgroup limit for a container.

CONTAINER OR MACOS GUEST?

  Start with the port. It usually decides on its own:

      jsc-*, gtk-*, wpe-*     Linux ports, clang, CMake      -> container
      mac-*, ios-sim-*        Xcode and a macOS SDK          -> vm

  `wk build --list` is the full config table. If the port leaves you a choice,
  these are the differences that matter:

  cost to create    container: one overlay mount, seconds, near-zero disk --
                    regardless of checkout size.
                    vm: an APFS clone of the golden base, also seconds -- but
                    the base has to exist first, and building it is hours
                    (image pull, Xcode, a checkout and a full mac-release) and
                    the largest thing on the machine (162 GB measured here).
                    Build one once with `wk vm base`; `wk disk` says what it
                    costs today.
  how many at once  container: as many as the machine will hold.
                    vm: Apple's licence permits two *running* guests per host
                    and Virtualization.framework enforces it -- a third fails
                    with VZErrorDomain code 6. Created guests are unlimited;
                    `wk vm stop` frees a slot.
  the sandbox       both are sandboxed, differently, and `wk claude` runs in
                    either. A container has no network interface at all and
                    reaches the allowlist through a unix socket; `wk verify`
                    proves that from inside. A guest is filtered from the host
                    by Softnet instead, which is why `wk verify` does not apply
                    to it -- and why `./setup --stage softnet` has to have run:
                    until it has, `wk vm start` refuses to boot a guest at all
                    (WK_VM_UNFILTERED=1 is the explicit, loud override), and
                    `wk claude` refuses a guest booted that way.
  display and GPU   only the guest has one. A container workspace on a macOS
                    host has no display and cannot get one (the podman VM has
                    no GPU, and there is no compositor to draw into), so
                    `wk gui` and `--zed` are refused there and say so. On Linux
                    a container gets the real seat and the real GPU.
  32-bit            `wk new --arch armhf` is a native 32-bit *container*, and
                    only on the Linux workstation -- Apple Silicon cannot
                    execute AArch32 at all.

  Neither is more disposable than the other: `wk rm` reclaims everything a
  workspace created, in both cases.

WHEN TO USE A BUILD MACHINE INSTEAD

  A remote target is for the builds this machine should not be doing: a full
  WebKit build on 80 or 128 cores, or a port whose toolchain lives over there.
  What you give up is the boundary -- it is somebody else's shared machine,
  your own uid, other people's work on the same filesystem. So `wk verify`
  refuses it (there is nothing to measure) and `wk claude` makes you force past
  a barrier that says exactly that. Builds there are niced to the floor, sized
  from that machine's live load, and serialised against your own other builds.

WHERE A COMMAND RUNS, ON A MACOS HOST

  Only container workspaces live inside the podman VM, so only their commands
  are forwarded into it over `podman machine ssh`; vm and remote workspaces are
  driven from the host. This is why a stopped podman machine is reported rather
  than started for a listing, and why `wk gui` on a container workspace here
  fails as a refusal with a reason instead of a missing display inside a Linux
  VM. `wk <command> --explain` prints which of the two a given command is.
