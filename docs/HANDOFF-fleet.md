- [ ] nothing in this fleet can power a Pi on (moose has a BMC; the boards do not), so "never touch the boards" is not literally met [hardware]
- [ ] `MACH_MAC` holds one address while a board can present another: rpi4's conf named eth0 (…:8a, down, no cable) and the board is on wlan0 (…:8b), so `wk find rpi4` swept the right subnet for an address the board never shows and reported "is on none of the segments … Either it is powered off" -- with the board up and answering ssh (2026-09-03). It also says "nothing here is stale", which is what makes the false negative convincing. Hold every address a board can present, or pick by `MACH_NET`; check rpi3's conf against its wlan0 address for the same fault [no hardware needed]
- [ ] the yocto bench and rescue images keep a volatile journal, so a board that hangs during boot leaves nothing to read after the power cycle that fixes it: rpi4 went silent mid-`--back` on 2026-09-03 and `journalctl` for that window is `-- No entries --`, one boot id only. Persist it (`Storage=persistent`) in the image, which is a rebuild, or have `wk pi` set it on a running system [no hardware needed]
- [ ] no Pi bench board arms the bootloader's own watchdog, so a hang before the OS starts costs a trip to the board: rpi4 wedged mid-`--back` on 2026-09-03 after ~20 reboots in one A/B and lost round 5. That is raspberrypi/firmware#1559, open and intermittent, and it reproduces there with nothing attached -- ruled out here: bootloader 2026/05/17 (past the pieeprom-2023-05-11 clock-init fix), BOOT_ORDER=0xf41 sd-first, no staging left on the SD, throttled=0x0, and the only hub is the VL805's onboard one. The remedy is firmware-enforced rather than ours: `BOOT_WATCHDOG_TIMEOUT` (seconds) resets the board when the OS has not started, which is exactly this failure; it is cancelled once the Arm CPU starts, so it guards the boot and nothing after it. rpi4's EEPROM sets no watchdog at all today. Pair it with MAX_RESTARTS, since 0xf41 already ends in the RESTART loop. Verify by reproducing a hang rather than assuming: one CM4 report had a kernel-armed BCM watchdog reset by the hang and never firing (that was not BOOT_WATCHDOG_TIMEOUT, which the bootloader arms itself) [needs a hand at the rpi4 to confirm; the EEPROM write itself is remote]
