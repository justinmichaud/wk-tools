- [ ] rpi4: why the kernel buildroot builds from the release-pinned rpi-5.15.y tree never reaches userspace on that board. Measured 2026-08-31 by staging one kernel at a time over the tryboot lane with everything else held identical -- a Raspberry Pi published kernel boots it, the built one does not, not even with the known-good device tree and no display overlay, and the built config lacks nothing a Pi 4 needs (ARCH_BCM2835, MMC_SDHCI_IPROC, PCIE_BRCMSTB, LPAE, HIGHMEM, SMP). What is left is the 2020.02 fork's gcc 9.2. The profile pins a kernel instead (BR_KERNEL_DEB_URL), so this is a question, not a blockage; answering it needs a serial console at the board, since the hang is before any console the network can carry [needs the rpi4 and a USB-serial adapter]

- [ ] rpi4: KMS comes up on the 2.52 yocto bench system intermittently, and nothing yet says why. Two boots of the *same* system from the *same* staged tryboot files (webkit-2.52-yocto-rpi4-64-fa57af516940 on /dev/sda3-4, os_prefix=second/, dtoverlay=vc4-kms-v3d, vc4 built into the kernel per modules.builtin): 2026-09-01 14:07 came up with `/sys/class/drm` holding nothing but `version`, no vc4 probe in dmesg, and weston.service exiting 1 -- `wk pi bench` died at the compositor; 15:53 came up with card0 (both HDMIs, Writeback), card1 and renderD128, weston on DRM with the GL renderer, and Speedometer running. The `fb` and `firmwarekms@7e600000` nodes are present in both and prove nothing -- they are in the base dtb. The one known difference is that the second boot followed a power cycle rather than a warm reboot, having found the tryboot flag still set from the boot that hung. Until this is understood, a leg of an `--ab-systems` run can lose its display for no reason the report can name [needs the rpi4 and repeated boots]

- [ ] rpi4 drops off the network under write load, and this is the one thing left unexplained about that board. Three times on 2026-09-01 it went from answering to no-route-to-host with nothing logged: once a minute after `modprobe vc4`, once during a reboot, and once mid-`scp` while staging the EEPROM update (the transfer died with "Connection closed" and the board never came back). Its root is on an Emtec USB stick, and a stick that drops off the bus takes the running system with it instantly, which fits the evidence better than any software cause -- the bench system, the rescue and the tryboot lane were each blamed for it in turn today and none of them was. Read `dmesg` for USB resets after the next drop, and try a fast SSD in its place (rpi4.conf already calls the stick a placeholder for one) [needs the rpi4 and a hand on its power]
- [ ] rpi4's EEPROM is still `BOOT_ORDER=0xf14` (usb-first) and that is now known to break the lane, not merely to be untidy: once a bench system with Pi-4-bootable boot files exists on the stick (the 2.52 yocto write put `start4.elf` and `kernel8.img` there), the firmware MSD-boots the stick on every boot and cold power cycle, so the board never returns to its rescue and every `--ab-systems` leg switch loses its leg. `wk pi boot-order rpi4 sd-first` is the fix; it got as far as staging `pieeprom.upd` and `pieeprom.sig` on the boot filesystem before the board dropped, so `recovery.bin` -- the trigger, copied last on purpose -- never landed and the EEPROM is unchanged. Re-run it once the board is up [needs the rpi4]
- [ ] a rescue whose root reference was orphaned (a card written before the disk identifier was carried across the shared-layout migration) is repaired from a reader with the helper's own verb -- `sudo -n /usr/local/libexec/wk-card-priv retarget <device>`, which rewrites partition 1's cmdline.txt and partition 2's fstab to the identifier the card now has. Decide whether that deserves a `wk` verb of its own or stays the one-liner a fixed migration should never need again [decision]
